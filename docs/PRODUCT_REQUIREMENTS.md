# 产品需求

## 1. 产品定义

Eternal Chat 是面向普通用户、研究型用户和开发者的现代 AI 桌面客户端。它不以“厂商列表最多”为目标，而以以下四件事为核心价值：

1. 模型在后续轮次中继续获得真实、完整、可审计的上下文。
2. 用户能够配置任何中转站、端口、协议、模型、能力、参数和工具，不受内置目录限制。
3. 长对话、长思考和复杂搜索过程仍保持清晰、流畅和可控。
4. UI、交互和工作流具有现代感，并提供足够深的个性化和客制化能力。

## 2. 目标用户

### 2.1 普通对话用户

希望像使用成熟桌面软件一样完成 Provider 配置、模型切换、历史搜索、主题切换、快捷键和导入导出，不需要理解 API 协议。

### 2.2 强资料依赖型用户

需要通过搜索、文件、数据库、MCP 或其他工具完成多步骤研究、校对、整合和决策。对这类用户，历史工具结果是否真实进入下一轮上下文比界面上是否显示工具卡片更重要。

### 2.3 模型与 API 高级用户

使用 NewAPI 等私有中转、OpenAI Chat Completions / Responses 兼容接口、实验模型、旧型号或未被主流客户端收录的模型，需要透传 `reasoning_effort`、`reasoning.effort`、`thinking`、`extra_body`、内置工具 descriptor 和自定义 Header。

### 2.4 Grok 搜索与多代理用户

希望看到 API 实际返回的思考、代理协作、搜索查询、工具结果、信源、耗时和响应状态，并能在后续轮次继续利用这些事实。

### 2.5 中转站与不稳定网络用户

高峰期可能遇到 429、临时 5xx、连接中断和首包超时，需要可配置、可取消、可审计的自动重试，而不是频繁手动重新发送或由客户端无限重试。

### 2.6 深度客制化用户

希望调整主题、字体、阅读宽度、密度、侧栏和面板布局、消息呈现、快捷键、动效强度、默认折叠规则，以及每个端点和模型的完整 wire 配置。

## 3. 核心用户任务

| 用户任务 | 成功结果 |
|---|---|
| 添加自定义中转站 | 在一个连接下配置一个或多个 URL、显式端口、路径和认证绑定 |
| 配置混合协议 | 同一连接的不同端点分别使用 Chat、Responses、Messages、Gemini 原生或自定义 profile |
| 添加未知模型 | 不依赖内置白名单即可使用并配置参数 |
| 设置 Grok `xhigh` | 请求预览和实际请求体均包含用户指定值 |
| 配置模型思考与内置工具 | 按当前 endpoint 显示正确 path，并可开关 web/X/Google/Anthropic search |
| 遇到 429 或临时上游故障 | 按 Retry-After/退避自动重试，显示 attempt 和倒计时，达到上限后明确失败 |
| 进行多轮工具研究 | 下一轮请求仍包含之前的工具调用与真实工具结果 |
| 查看搜索过程 | 可看到查询、工具状态、结果数量、信源和耗时 |
| 处理超长会话 | UI 保持流畅，模型上下文策略明确且无静默裁剪 |
| 停止或恢复生成 | 状态终止一致，部分内容可保存，不产生悬挂流 |
| 编辑或重新生成 | 保留旧版本并形成可导航分支，不覆盖历史 |
| 客制化界面 | 主题、密度、字体、布局、消息和动效偏好可保存并即时预览 |
| 排查问题 | 能查看最终 URL、协议、请求参数、上下文清单、事件和错误 |

## 4. 产品原则

### 4.1 模型实际输入高于 UI 表象

UI 显示的历史、数据库保存的历史和实际发送给模型的历史必须有明确映射。任何无法发送给模型的块都要在上下文检查器中标记原因。

### 4.2 不进行隐形能力降级

- 不因模型不在内置列表中而隐藏参数控件。
- 不因客户端无法识别未知字段而删除它。
- 不因上下文很长而无提示删除旧消息或工具结果。
- 不因流式解析失败而把“没有解析到”当成“Provider 没有返回”。
- 不因请求失败而静默降低思考档位、删除工具或切换模型/端点。
- 不把无限重试包装成“稳定性”；重试次数、原因、等待和费用风险必须可见。

### 4.3 默认简单，高级能力随时可达

普通用户看到的是连接、端点、模型和常用参数。高级用户可以展开协议 profile、schema 编辑、原始请求体、自定义 Header、请求预览和上下文检查器。高级能力不能影响默认配置流程的清晰度。

### 4.4 协议与厂商解耦

- Provider 是连接分组，不是协议枚举。
- 每个端点独立配置 URL、端口、路径、protocol profile 和请求映射。
- 模型名、公司名和图标只能提供建议，不能决定参数或工具开关。
- UI 语义标签与 wire key/path 分离；用户可以自行定义实际字段。

### 4.5 现代、直接、可中断的交互

- 反馈从 pointer-down 开始，不能等命令完成后才有反应。
- 拖拽、抽屉、面板和切换动效从当前屏幕状态继续，允许中途打断和反向。
- 进入与退出保持空间一致，面板从触发源建立清楚关系。
- 动效服务于状态理解和操作连续性，不堆叠装饰动画。
- reduced motion 使用短交叉淡入或即时状态变化，保留反馈但去除位移和弹性。

### 4.6 深度客制化

- 用户可以调整主题、字体、字号、行高、阅读列宽、信息密度、侧栏宽度、面板位置和消息表现。
- 用户可以配置快捷键、发送行为、工具/思考/来源的默认折叠状态和动效强度。
- Provider、端点、模型和会话均可保存不同参数与工具 preset。
- 所有客制化都有恢复默认和按作用域覆盖能力。

### 4.7 本地优先

会话、消息、参数 schema、附件引用、搜索索引和审计快照默认保存在本机。除用户配置的模型 API、更新服务和显式启用的后续同步模块外，不连接其他服务。

### 4.8 可见失败

网络失败、参数拒绝、上下文超限、工具结果缺失、流被中断、Provider anchor 失效和解析不兼容都必须形成明确错误状态，不能以空内容或模型自然语言掩盖。

## 5. MVP 功能范围

### 5.1 核心聊天

- 新建、重命名、归档、删除和搜索会话。
- 文本流式生成、停止、重试、编辑、重新生成和分支切换。
- 按明确错误分类执行的自动重试；手动重新生成与网络 attempt 明确区分。
- Markdown、代码块、表格、链接、数学公式和复制。
- 思考块、工具块、错误块、用量和完成原因。
- 当前会话模型、系统提示词、参数和 `extra_body`。

详细规格见 [核心聊天与分支](./features/01-core-chat-and-branching.md)。

### 5.2 Provider、端点与模型管理

- 连接分组与多个独立端点；每个端点支持显式端口、路径、协议、认证、Header 和 Query。
- OpenAI Chat、Responses、Anthropic Messages、Gemini generateContent/Interactions 和自定义 JSON/SSE profile。
- 端点连接测试、模型列表拉取和手工模型添加。
- 全量能力、参数、工具和响应映射 schema，支持模型级与会话级覆盖。
- GPT、Grok、Gemini、Claude 官方 preset 与可编辑 wire key/path；模型品牌不绑定协议。
- 所有官方请求字段都能从专用控件、高级 schema 或 raw override 访问。
- 请求预览显示最终 URL、端口、protocol revision、Header、Query、Body、工具和字段来源。

详细规格见 [Provider 与模型管理](./features/02-provider-and-model-management.md)。

### 5.3 上下文与工具连续性

- 当前分支路径选择。
- 工具调用和工具结果的持久化与 Provider 协议重建。
- 请求上下文清单和块哈希。
- 默认 lossless，不静默裁剪。
- 上下文超限时的可见处理流程。

详细规格见 [上下文与工具连续性](./features/03-context-and-tool-continuity.md)。

### 5.4 思考、搜索与信源

- Provider 返回的可见思考内容。
- Grok 搜索查询、工具使用、结果、代理或 rollout 标识、来源和耗时。
- Provider 内置工具的 `off | auto | required` 意图；只有 endpoint 真正支持时才提供 required。
- 流式中与完成后的不同展示状态。
- 信源列表、去重、外链和引用定位。

详细规格见 [思考、搜索与信源](./features/04-reasoning-search-and-sources.md)。

### 5.5 会话库与本地数据

- 最近会话、归档、全文搜索、分页加载。
- JSON 导入导出和基础备份。
- 数据迁移、损坏检测和恢复提示。
- 设置、主题、快捷键和更新入口。

详细规格见 [会话库与搜索](./features/05-conversation-library-and-search.md) 与 [设置与本地数据](./features/06-settings-security-and-data.md)。安全专题当前 `deferred`。

### 5.6 自动重试与请求尝试

- 应用默认和 endpoint 级重试设置。
- 默认处理临时连接失败、连接/首包超时、408、429、500、502、503、504。
- 尊重 `Retry-After`，否则指数退避 + full jitter。
- 同一 logical request 下保存多个 request attempt；参数、上下文和 body hash 固定。
- 已收到 response id、reasoning、text、tool、source 等有价值事件后默认不从头自动重发。
- 用户可以停止等待，并查看 attempt 次数、原因、倒计时和最终错误。

详细规格见 [自动重试与请求尝试](./features/16-automatic-retry.md)。

## 8. 明确非目标

- 不做云端账号体系作为 MVP 前置条件。
- 不因模仿参考项目而加入浏览器自动化、多代理编排、RAG、向量数据库或任务调度器。
- 不在第一版实现跨设备实时同步。
- 不承诺展示 Provider 从未通过 API 返回的隐藏内部思维过程。
- 不使用模型名称硬编码决定全部能力。
- 不把工具结果只保存为截图、卡片或自然语言摘要。
- 不在 MVP 自动切换 Provider、账号或模型作为重试的一部分。

## 9. 关键用户流程

### 9.1 首次配置

1. 用户进入连接与端点页面。
2. 创建连接分组，并添加一个端点的 URL、显式端口和路径。
3. 选择 OpenAI Chat、Responses、Anthropic Messages、Gemini 原生或自定义 protocol profile。
4. 配置认证绑定、Header、Query 和连接参数后执行最小测试。
5. 用户可拉取模型列表，也可直接手工添加模型 ID。
6. 客户端提供来源明确的建议 schema，但用户可以 fork、编辑或从空 schema 开始。
7. 请求预览确认最终 wire 内容后创建第一个会话。

失败时必须保留用户输入并显示可操作原因，不能只显示“连接失败”。

### 9.2 未知 Grok 模型设置 `xhigh`

1. 用户添加一个内置目录中不存在的模型。
2. 为 `grok-4.20-multi-agent` 选择 Responses endpoint，在模型 schema 中增加 `reasoning.effort`，选项包含 `xhigh`，或直接在 `extra_body` 中设置。
3. 请求预览显示最终合并结果和参数来源。
4. 发送后请求快照保存参数、端点和 protocol revision。
5. UI 说明 `high/xhigh` 对应官方 16 agents 档位，而非普通推理深度。
6. 如果 Provider 拒绝，错误面板显示 HTTP 状态、Provider 错误代码和可展开响应片段，不回退成其他档位。

### 9.3 强资料依赖型多轮任务

1. 第一轮模型调用搜索或 MCP 工具。
2. 客户端保存工具名称、参数、原始结果、模型可见结果、状态和关联 ID。
3. 助手第一轮最终文本不必复述全部工具结果。
4. 第二轮用户要求基于某个只存在于工具结果中的字段继续分析。
5. 上下文构造器重新生成 Provider 所需的工具调用和工具结果块。
6. 开发者模式可证明第二轮实际请求包含该结果。

第 5 步失败即为阻断发布的 P0 缺陷。

### 9.4 长思考与搜索

1. 请求开始后显示运行状态和计时。
2. Provider 返回 reasoning、tool usage、tool result、citation 等事件时按顺序追加。
3. 用户可以展开查看完整的 Provider 可见内容，也可以折叠只看摘要。
4. 最终答案与思考/搜索区域分离，引用可以定位到来源。
5. 完成后计时冻结，历史事件持久化，重新打开会话仍可查看。

### 9.5 429 自动重试

1. 用户通过启用自动重试的 NewAPI Provider 发送消息。
2. 第一次 attempt 在任何 Provider 有价值事件前返回 429 和 `Retry-After`。
3. 同一个 assistant placeholder 显示 `第 2 / 4 次尝试`、失败原因和倒计时。
4. 用户可以停止；未停止时在规定时间后用相同 ContextManifest、参数和 body hash 重试。
5. 成功后只形成一条 assistant 消息，历史详情中保留全部 attempts。
6. 如果已经出现 reasoning、tool 或 text 后断流，客户端保留部分内容并要求用户决定，不自动从头重发。

## 10. 非功能需求

| 类别 | 需求 |
|---|---|
| 真实性 | UI、数据库和模型请求之间存在可验证映射 |
| 性能 | 1000 条种子会话仍可流式输入、滚动和切换 |
| 稳定性 | 取消、断流、解析错误、自动重试和重启不能留下永久 `streaming`/`waiting_retry` 状态 |
| 可移植性 | Provider 与业务逻辑保持 TypeScript，可在 1-2 天内替换桌面壳 |
| 无障碍 | 键盘可操作、焦点可见、状态可被读屏读取、支持 reduced motion |
| 现代交互 | 反馈即时、动效可中断、路径一致、滚动/拖拽稳定且无布局跳动 |
| 客制化 | UI、连接、端点、协议、能力、参数和工具均支持作用域化覆盖与恢复默认 |
| 可维护性 | wire 行为由小型 codec/profile 和 fixture 测试隔离 |
| 可诊断性 | 最终 URL、端口、协议、参数来源、兼容状态、上下文清单和终止原因可查看 |

## 11. 产品级验收

MVP 对外标记为可用前，以下条件必须同时满足：

- 至少三个不同 protocol profile 通过基础对话验收，其中一个场景必须是“模型品牌与协议不一致”的中转配置。
- 同一连接的两个不同端口可以使用不同协议并分别保存模型。
- 未知模型能够设置并透传非内置参数值。
- Chat Completions 与 Responses 基础聊天均有本地契约测试和至少一个真实兼容端点冒烟。
- GPT、Grok、Gemini、Claude 的思考 preset 和至少一个对应内置搜索工具 descriptor 通过 fixture。
- 官方 API request 字段目录具有覆盖率报告；没有专用 UI 的字段仍可编辑。
- 至少验证一个参数报错、一个参数被静默忽略和一个未知行为，且客户端不自动删字段。
- 429/5xx/网络错误自动重试矩阵通过，收到部分输出后不自动从头重发。
- 工具结果跨轮回放 canary 测试通过。
- 用户关闭窗口、停止生成和网络中断后不会残留不可恢复的流式状态。
- 1000 条消息性能场景通过文档预算。
- 数据库从至少一个旧 schema fixture 升级到当前版本成功。
- 根 README、功能状态和实际代码一致，没有把 deferred 功能写成已完成。

## 12. 成功指标

第一阶段不以消息数量或使用时长作为主要成功指标。更有价值的指标包括：

- Provider 首次配置成功率。
- 端点/协议 profile 首次配置成功率。
- 自定义模型和参数请求成功率。
- 参数 rejected/ignored/unknown 分类准确率。
- 自动重试恢复率、平均 attempt 数和 retry budget exhausted 比例。
- 取消后恢复成功率。
- 长会话内存曲线稳定性。
- 上下文检查器中“不可回放块”的发生率。
- 工具结果跨轮连续性自动化测试通过率。
- 错误是否具有可操作原因，而非通用失败提示。

这些指标的采集方式在实现阶段另行决定；当前首先通过本地自动化、可重复 fixture 和用户主动反馈验证。
