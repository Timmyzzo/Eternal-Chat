# 性能与资源预算

## 1. 目标

“长对话不卡”必须由可重复测量证明。性能优化不能以删除模型上下文、降低工具事实完整性或隐藏功能为代价。

## 2. 两个必须分开的窗口

| 窗口 | 用途 | 默认策略 |
|---|---|---|
| UI 内存窗口 | 控制 DOM、React 对象和 Markdown 缓存 | 最近约 300 条，按需换页 |
| 模型上下文窗口 | 决定发给模型的语义历史 | 默认 lossless，显式预算处理 |

任何实现把这两者使用同一个 `messages.slice(-N)`，都视为 P0 架构缺陷。

## 3. 基准数据集

建立确定性种子脚本，至少生成：

- 1 个 1000 条消息会话。
- 普通短消息、Markdown 表格、列表和引用混合。
- 1 条 5 万字 AI 回复。
- 20 个代码块，覆盖常见语言。
- 50 个思考块。
- 100 次工具调用，其中包含搜索来源和失败结果。
- 20 个分支节点。
- 若干附件元数据，不必加载真实大文件。

性能测试使用固定 seed，结果记录应用版本、操作系统、CPU、内存、WebView 版本和是否开发构建。

## 4. 目标预算

这些值是第一版工程目标，建立真实基线后可以在不放宽用户体验的前提下调整。

| 指标 | 目标 | 阻断线 |
|---|---|---|
| 冷启动到可交互 | 2.5s 内 | 5s 以上 |
| 打开普通会话 | 200ms 内 | 750ms 以上 |
| 打开 1000 条会话最近页 | 350ms 内 | 1s 以上 |
| 会话切换主线程长任务 | 无连续 >100ms | 存在 >300ms |
| 流式时输入延迟 p95 | 50ms 内 | 150ms 以上 |
| 快速滚动可见帧率 | 大部分时间 >=55 FPS | 持续低于 40 FPS |
| Rust -> WebView 批次频率 | 通常 <=40 次/秒 | 持续 >80 次/秒 |
| 流式 Markdown 重解析 | 约 50ms 节流 | 每 token 全量解析 |
| 初始消息加载 | 50 条 | 一次加载整个会话 |
| UI 内存消息窗口 | 约 300 条 | 随会话长度无限增长 |
| 新建空会话稳定内存 | 参考目标 100-220MB | 常态超过 300MB 需调查 |
| 30 分钟长流内存增长 | 稳定后不持续爬升，净增 <30MB | 单调增长且不可回收 |
| 100 次会话切换后增长 | 回落后 <20MB | 每次切换持续累积 |

绝对内存受 WebView、平台和调试工具影响，因此必须同时看趋势。一次峰值不是泄漏，无法回落的单调增长才是重点。

## 5. 渲染预算

### 5.1 虚拟列表

- 只渲染视口附近消息。
- 动态高度测量结果缓存。
- 消息展开/折叠后只重测受影响项。
- 流式消息放在列表尾部独立渲染，避免每个 delta 重建全部 item data。
- 上方加载页保持 scroll anchor。

### 5.2 React 更新

- history 与 streaming store 分离。
- 历史 MessageItem 使用稳定 key、memo 和按 ID selector。
- 输入框、侧栏、右侧面板不订阅完整 streaming object。
- 高频计时只更新局部状态，不触发 Markdown 正文重渲染。
- 自动重试倒计时最多按 1 秒级更新局部状态；attempt 详情关闭时不持续渲染完整时间线。
- source/tool 数组更新使用稳定 ID 和增量 reducer。

测试中应使用 React Profiler 或等价计数断言：一个 text delta 不应让 50 个历史 MessageItem 重新 render。

## 6. Markdown 预算

- 已完成消息按 `messageId + blocksVersion + theme/renderOptionsVersion` 缓存 HTML/AST。
- 流式正文约 50ms 节流解析。
- 未闭合代码块先按纯文本/轻量 code block 渲染。
- shiki 在消息完成或代码块闭合后懒加载并异步高亮。
- KaTeX、mermaid 和其他重型插件按内容检测动态 import。
- 缓存使用有界 LRU，不因访问 1000 条消息永久保留所有 HTML。
- 消息编辑、主题影响和设置变化必须精确失效相关缓存。

## 7. IPC 与网络预算

- Rust 约 30ms 合批，或累计 64 条立即发送。
- 单个 batch 的 UTF-8 data payload 上限为 256 KiB；单个原始 data 事件不得被拆分，超过上限时以流错误终止，避免超大事件阻塞主线程。
- 大型 raw artifact 通过文件引用或独立分页读取，不经 Channel 反复传输。
- 不在前后端之间传整个会话对象。
- 取消事件优先处理，不能被大批量 delta 长时间排队。

## 8. SQLite 预算

- 打开会话使用索引和游标分页。
- 流式 token 不逐条事务写库。
- 可以每 1-2 秒或达到一定字符量保存恢复检查点，最终频率由测量确定。
- 搜索、标题生成、FTS 重建和附件清理放在空闲或后台任务，不阻塞当前输入。
- SQL 查询需有 explain/索引检查，避免消息数增加后退化为全表扫描。

## 9. 内存所有权

需要明确释放：

- 已离开会话的 streaming parser buffer。
- Channel listener 和 Tauri event unlisten。
- AbortController/cancellation token。
- Markdown AST/HTML LRU 旧项。
- 图片 object URL。
- shiki highlighter 主题/语言缓存的上限。
- 工具 raw result 临时对象。
- 计时器、observer 和 intersection/resize observer。
- retry backoff timer、fake/real clock subscription 和已取消 attempt 回调。

开发模式可提供按会话/请求计数的诊断摘要，帮助定位泄漏所有权。

## 10. 性能测试场景

### P1 流式输入

1000 条会话停在底部，模拟每秒高频 token 60 秒。持续在输入框打字，记录输入延迟、render 次数、批次率和内存。

### P2 快速滚动

从底部快速滚到顶部再返回，展开思考和工具块。检查帧率、白屏、跳动和重复加载。

### P3 会话切换

在 20 个长短不同会话间循环切换 100 次。检查内存回落、listener 数量和数据库查询时间。

### P4 超长消息

打开 5 万字、20 代码块消息，进入/离开视口，切换主题，复制内容。检查主线程长任务和缓存。

### P5 长时间运行

应用打开 2 小时，执行多轮流式、停止、切换和空闲。比较稳定内存、句柄、timer 和 DB 连接。

### P6 大型工具结果

工具返回 5-20MB raw artifact，但 modelContent 有受控大小。验证 UI 不把 raw object 常驻 store，Channel 不传全量重复副本。

### P7 重试风暴与取消

模拟 20 个会话依次遇到 429/503，但同一会话仍只允许一个 active logical request。反复进入 waiting_retry、停止和切换会话，检查 timer/listener 数量回落、CPU 空闲、attempt 详情按需加载，并确认没有后台无限重试。

## 11. 性能回归门禁

- PR/阶段完成时运行可重复的轻量 benchmark。
- 发布候选运行完整场景并保存基线 JSON/截图。
- 指标超过阻断线必须调查，不能用提高阈值直接通过。
- 性能修复必须说明没有改变 ContextManifest 和模型实际输入。
- 依赖升级涉及 Markdown、虚拟列表、React、Tauri 或 SQLite 时必须重新跑相关基准。

## 12. 诊断输出

性能诊断包可以包含：

- 应用/平台/WebView 版本。
- 消息数量、已加载页数、可见 DOM 节点数。
- stream batch 数、平均 batch 大小。
- render 计数、缓存命中率。
- SQLite 查询耗时摘要。
- 内存采样趋势。

诊断包是否包含消息、工具结果或请求字段属于后续安全与隐私专题，不作为性能验收的一部分；性能数据结构必须能独立记录计数、时长和资源趋势。

## 13. 验收

“性能完成”不是一次手动感觉顺滑。至少需要：固定 seed、自动化指标输出、长时间内存曲线、React render 证据和多视口人工检查。任何通过删除历史工具结果或缩短模型上下文得到的性能提升均无效。
