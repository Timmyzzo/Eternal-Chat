# 基线与决策治理

## 1. 文档目的

本文件定义 Eternal Chat 当前的决策边界。旧版单体设计文档已经完成总览作用并删除；根 README、本文和 `docs/` 下的专题规范共同组成当前唯一基线。

## 2. 决策优先级

| 优先级 | 来源 | 处理方式 |
|---|---|---|
| 1 | 用户最新、明确的要求 | 立即以最新要求为准，并同步所有受影响文档 |
| 2 | 当前专题规范与已接受项目决定 | 约束实现、测试和验收，不能被代码现状静默覆盖 |
| 3 | 官方最新产品/API 文档 | 决定会变化的模型、端点、参数、工具和错误事实 |
| 4 | 当前任务相关的 Cherry 用户文档与开发者 `docs` | 作为非差异化产品和工程设计的首要外部范本，不能覆盖前 3 项 |
| 5 | 已接受 ADR、可重复验证证据和其他外部资料 | 细化实现选择；需要写回规范才成为项目决定 |
| 6 | 当前实现 | 必须服从上层规范，不能自我授权 |

当官方资料与内置 preset 不一致时，官方资料决定新的内置 revision；用户已经编辑的本地版本仍保持最高配置优先级。若中转站行为与官方端点不同，以该端点的实际可重复探测结果和用户覆盖为准，不按模型品牌猜测。

## 3. 当前已接受的项目决定

### 3.1 产品与体验

- 产品应具有现代感，不只体现在配色，还包括信息架构、反馈速度、动效、手势、空间关系和工作流效率。
- UI 采用 Apple 风格的设计原则作为方法参考：即时响应、连续反馈、可中断动效、速度继承、空间一致性、克制材质和 reduced-motion 等价体验；不复制具体系统界面。
- 用户应尽可能掌握界面、布局、主题、阅读密度、快捷键、消息显示、参数面板和模型行为的客制化权。
- 默认路径保持清晰，但任何高级协议、参数、工具和请求细节都必须随时可达，不能因“简洁”被删掉。

### 3.2 Provider、端点和协议

- Provider 只是用户命名的中转站、账号或连接分组，不代表协议，也不等于模型厂商。
- 一个 Provider 可以包含多个端点；每个端点独立拥有 URL、显式端口、路径、方法、协议 preset、认证、Header、Query、超时和重试配置。
- 同一个模型可以通过不同端点使用 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini generateContent/Interactions 或用户自定义 JSON/SSE 映射。
- `vendorHint`、模型名和远程目录只提供显示与建议，不得决定最终请求格式、参数列表或能力开关。
- 内置协议 codec 提供可靠默认值；用户可以 fork、编辑或从空 profile 开始。实现不得用厂商硬识别覆盖用户选择。

### 3.3 参数、能力和工具

- 参数 schema、能力 schema、工具 descriptor 和 wire mapping 都是数据，不是散落在组件中的模型名判断。
- UI 可以显示“温度”“Top K”“努力程度/思考预算”等稳定语义标签，但实际 key、path、位置、类型、枚举、默认值和 omit 规则完全可编辑。
- tooltip 可以列出官方常见写法，例如 `effort`、`reasoning_effort`、`reasoning.effort`、`reasoningEffort`、`thinkingLevel`、`thinkingBudget`、`output_config.effort`；这些只是示例，不触发自动改名。
- 内置目录是便利数据，不是能力白名单。目录外模型、未知参数、未知工具和未知枚举值必须能够配置和发送。
- 不支持参数的行为不能预设为“忽略”或“报错”。端点可记录 `accepted_effective`、`accepted_ignored`、`rejected`、`translated` 或 `unknown`，并保留探测证据。

#### 3.3.1 模型支持范围

Eternal Chat 不以覆盖所有历史模型和历史参数组合为目标。模型适配采用三级范围：

| 支持级别 | 范围 | 项目责任 |
|---|---|---|
| 主动支持 | 当前发布周期内仍属主流、官方推荐且进入内置目录的模型 | 维护最新官方来源、内置 preset、参数定义、兼容证据和发布回归测试 |
| 特殊支持 | 虽非当前主流，但仍有不可替代能力或已确认真实需求的模型 | 通过明确决定加入有限 preset 和针对性测试，不因“历史型号”自动进入 |
| 尽力兼容 | 其他旧模型、目录外模型、自定义模型和中转站 model alias | 允许配置和发送，初始兼容状态为 `unknown`；展示原始响应与错误，但不承诺专用 preset、完整兼容矩阵或发布门禁 |

“不主动适配旧模型”不等于假定旧模型或旧字段不会产生兼容问题。Claude legacy thinking、Gemini 2.5 thinking budget 等历史案例只用于证明端点可能拒绝、忽略、兼容接受或转换字段；除非进入特殊支持范围，否则不要求为其增加专用 UI 分支、默认 preset 或逐版本回归测试。

无论模型属于哪一级，客户端都不得自动删除报错参数后重试，也不得把 HTTP 200 当作字段已生效的充分证据。尽力兼容模型可以由用户主动运行单字段最小探测，探测结论仍按 endpoint、model、API version 和 protocol profile revision 隔离。

### 3.4 上下文与数据真实性

- SQLite 中的消息块是下一轮请求上下文的权威来源，不只是 UI 展示数据。
- 当前分支上可回放的工具调用和工具结果必须按目标协议重新序列化。
- 默认上下文策略是 `lossless`，不进行隐藏裁剪或自动摘要。
- UI 虚拟化、分页和内存窗口不得改变模型实际上下文。
- 每次请求保存参数、端点、协议 profile、上下文清单、块/Body 哈希、profile/codec revision 和终止状态，以便核对实际发送内容。

### 3.5 技术方向

| 领域 | 当前决定 |
|---|---|
| 桌面架构 | Tauri 2 为主方案，Electron 只作为证据充分时的退路 |
| 前端 | React 19 + TypeScript + Vite |
| UI | Tailwind CSS + shadcn/ui + Radix + lucide-react；交互动效可采用 Motion 等小型 spring 库 |
| 状态 | Zustand，并按 selector 精准订阅 |
| 长列表 | virtua，必要时评估 `@tanstack/react-virtual` |
| Markdown | markdown-it，按消息缓存，流式时节流 |
| 数据 | SQLite，经 tauri-plugin-sql 由 TypeScript 直接访问 |
| 网络 | Rust 通用 HTTP/SSE 管道，只接收最终请求描述并回传原始事件 |
| Provider | TypeScript 薄 codec/profile 层，不用会吞未知字段的重型 SDK 作为核心主链 |
| 消息 | 块数组存储，思考、文本、工具、来源和附件保持结构化 |
| 分支 | `parent_id` 保存重新生成和编辑形成的分支树 |
| 性能 | 虚拟列表、流式状态隔离、缓存/节流、分页窗口、IPC 合批 |
| 模块化 | 核心仅聊天、连接/模型管理和设置；其余模块懒加载 |

### 3.7 Cherry Studio 参考生命周期

- Cherry 用户文档用于用户任务、配置流程、默认值解释、错误文案和功能发现的对照。
- Cherry 开发者 `docs` 是当前最重要的外部工程参考，尤其用于 AI 主链、流式管理、Provider 解析、消息树、数据边界、测试和诊断。
- 每个实现任务应按 [双文档参考指南](./CHERRY_STUDIO_REFERENCE_GUIDE.md) 读取对应页面，并记录共同契约、Eternal Chat 差异、采用项和拒绝项。
- Cherry 文档不能覆盖用户最新要求、Eternal Chat 的差异化决定、当前 Phase 边界或官方 API wire 事实。
- Cherry 源码目录保持只读；只吸收行为契约、不变量和验证方法，所有实现从零完成。
- Cherry-only 功能不会因为文档成熟而自动进入 MVP；必须经过独立规格和路线决策。

### 3.8 当前安全范围

- 安全、隐私、API Key 存储、日志脱敏、权限隔离、签名更新和威胁模型暂时不进入当前设计与 MVP 门禁。
- 当前规范不锁定 keyring、凭据持久化或最终授权注入方案；后续恢复安全专题时单独设计和迁移。
- 开发资料、测试和仓库仍不得包含真实凭据或私人数据。

## 4. 明确不采用的方向

| 方向 | 原因 |
|---|---|
| 用模型名称或公司身份决定协议和全部参数 | 同一模型可经不同中转协议暴露，结论会错误 |
| 把 Provider 固定成 OpenAI/Anthropic/Gemini 三种互斥类型 | 无法表达一个中转站的多个端口、端点和混合协议 |
| 把所有思考参数写成同一路径 | 各 endpoint、SDK 和网关字段名及嵌套位置不同 |
| 假设不支持参数必然被忽略或必然报错 | 官方端点实际同时存在忽略、报错、兼容接受和转换 |
| 因目录没有某模型而隐藏能力 | 无法适配实验模型、旧型号和私有网关 |
| 为节省 token 静默删除工具结果 | 破坏事实连续性，风险不可见 |
| 只在 UI 保存工具卡片 | 下一轮模型无法获得真实工具证据 |
| 重型 IoC、调度器或多进程业务层 | 当前核心范围不需要，增加常驻成本和维护复杂度 |
| 无限重试或已有输出后自动从头重发 | 可能重复计费、文本和工具副作用 |
| 复制参考项目源码、图标、品牌或素材 | 不属于本项目实现路径，并存在许可风险 |

## 5. 可调整但需记录的选择

- virtua 与 `@tanstack/react-virtual` 的最终选择。
- SQLite 是否启用 FTS5，以及不可用时的回退。
- markdown-it 插件集合和 spring 动效库。
- 参数 schema、声明式 wire mapping 和运行时校验库。
- 凭据的保存与授权注入方式；当前不作为开发前置。
- 是否在普通模式持久化原始 SSE，或只在开发者追踪模式保存。
- 第一版发布平台、签名/更新基础设施、产品名、图标和开源许可证。

这些选择不能借机改变协议与厂商解耦、用户配置优先、参数完整透传、工具连续性或现代交互原则。

## 6. 变更流程

涉及以下领域时，应先更新规范和测试计划，再修改代码：

- 端点 URL、端口、协议 profile、请求结构或参数优先级。
- 官方模型能力、工具版本、错误行为或 preset revision。
- 历史消息选择、裁剪、摘要或上下文预算。
- 工具调用、工具结果或 MCP 数据结构。
- 消息、分支、附件和迁移 schema。
- Rust/TypeScript 责任边界。
- 性能预算、布局和核心交互行为。

建议决策记录至少包含：

```text
标题
状态：proposed / accepted / rejected / superseded
背景与官方来源
约束
备选方案
决定
影响
验证
回滚方式
```

## 7. 基线完整性检查

每次大规模文档或实现变更后，应验证：

- 不再引用已经删除的旧版设计文档。
- Provider 显示身份没有被用作协议或参数硬开关。
- 显式端口、自定义路径和多个端点不会被 URL 正常化丢失。
- 参数、工具和 capability 的用户覆盖仍高于目录与厂商推断。
- 请求预览能显示最终 URL、协议、参数 key/path、工具 descriptor 和来源。
- 不支持参数行为保持 `unknown`，直到官方资料或真实探测证明。
- UI 规范同时覆盖现代视觉、即时反馈、可中断动效和 reduced motion。
- 安全专题仍为 `deferred`，没有重新成为当前里程碑的隐含门禁。
- 官方 preset 带来源、核对日期、适用范围和 revision，且没有覆盖用户编辑版本。
- 当前任务若涉及 Cherry 映射，已记录对应本地路径、在线链接、核对日期和采用/拒绝理由。
